# Obsidian用PURビューアー

PureRefの `.pur` を、Obsidianの保管庫から直接開き、画像配置を編集できるプラグインです。
Canvasへの事前変換や別アプリの起動は不要です。
コンテナー2.1 / DB世代200101に限り、編集結果を現在の `.pur` へ上書き保存できます。
別名保存も操作メニューに残しています。
画像の外部抽出は行いません。

デスクトップ版とAndroid版Obsidianの共通APIを使用します。
実行時のNode.js、外部ネイティブ実行ファイル、CDN、インターネット接続には依存しません。
v0.1.5について、ユーザーからデスクトップ版Obsidianで「開けるようになりました」と報告があり、今回の起動と表示の不具合は実機での解消を確認しました。
ユーザーはデスクトップ版の画像移動、拡縮、元に戻す、やり直すも確認しています。
v0.2.0の保存についても、ユーザーから「保存確認が取れました」と報告がありました。
その後、ユーザーから保存結果をPureRef本体でも開けたと報告がありました。
この報告はv0.2.0の出力に関するもので、すべてのPureRef世代やファイルへの互換性保証ではありません。
v0.3.2のグリッドと8個のハンドルについても、ユーザーから変更部分に問題はなさそうだと報告がありました。
選択時前面化、保存キー、自動保存、v0.6.0のバックアップ整理を含む上書き保存のObsidian実機動作、Android版での動作は未確認です。
v0.6.0からv0.8.3までの自動保存もObsidian実機では確認できていません。
v0.8.3の実機診断から、タイマー関数の呼び出し時に`Illegal invocation`が発生し、自動保存が予約されていなかった可能性が分かりました。
v0.8.4で呼び出し方を修正しましたが、Obsidian実機での自動保存は再確認が必要です。
ブラウザーでの検証やビルド成功を、Obsidian実機での動作保証とはしていません。
2026年11月6日、ユーザーからv0.10.0のSVGについて「SVGは問題なかったです」と実機報告がありました。
この報告はユーザーが試したSVGに関するもので、すべてのSVGや端末での保証ではありません。

## 導入方法

現時点ではコミュニティプラグイン一覧に登録していないため、手動で導入します。
開発用のNode.jsはビルド時だけ必要です。

リポジトリのルートで次を実行します。

```powershell
npm --prefix obsidian-pur ci
npm --prefix obsidian-pur run build
```

成果物は `obsidian-pur\dist\` に生成されます。
その中の `main.js`、`manifest.json`、`styles.css`、`THIRD-PARTY-NOTICES.txt` を、保管庫の `.obsidian\plugins\lazyref-pur\` にコピーしてください。
v0.12.0ではHEICデコーダーの対応ソースを含む `HEIC-SOURCES\` も配布物と一緒に保持し、再配布時は同梱してください。
このフォルダーはライセンスと再ビルドのためのもので、実行時には読み込みません。
プラグインフォルダー名はマニフェストのIDと同じ `lazyref-pur` にします。
`node_modules` やリポジトリ全体をコピーする必要はありません。

Androidでも、Obsidianが使用している保管庫内に同じフォルダーを配置します。
Androidのファイル管理アプリで隠しフォルダーを表示するか、PCからコピーしてください。
同期を使う場合、`.obsidian` 内のプラグインファイルも対象になっているか確認します。
保管庫の設定フォルダー名を変更している場合は、`.obsidian` をその名前に読み替えてください。

Obsidianを再起動し、「設定」の「コミュニティプラグイン」で制限モードを解除して「LazyRef PUR Viewer」を有効にします。
`.pur` を保管庫内へコピーし、ファイル一覧から開いてください。
クリックで開かない場合は、ファイルを右クリックして「Open with LazyRef PUR Viewer」を選んでください。
同じ拡張子を扱う別プラグインとは競合するため、併用しないでください。
プラグインを無効にしても、元ファイルはそのまま残ります。

コマンドパレットの「PURビューアーの診断情報を表示」で、ビルド番号が `0.12.0` であることを確認できます。
別の番号なら、Obsidianのプラグインフォルダーにある配布物が古い可能性があります。
コマンドパレットで「PURビューアーの診断情報を表示」を実行すると、プラグイン登録、起動要求、ビュー生成、ファイル読込と解析の到達段階を確認できます。
通常時はツールバー、ビルド番号、計測を非表示にし、描画領域を優先します。
「設定」→「LazyRef PUR Viewer」→「デバッグモード」（標準オフ）をオンにすると、開いているビューにもツールバーと読込計測を表示します。
v0.3.1では常設の警告と状態欄も通常モードから除き、デバッグモードと診断コマンドへ移しました。
保存失敗や競合は、通常モードでも一時通知で理由を表示します。
未保存判定と破棄確認は残しており、通常モードの状態欄を隠しても保存済み扱いにはしません。
`frame drawn` はCanvasへの描画処理の完了、`waiting for layout` は描画領域の幅または高さが0である状態です。
通常クリックでは専用メニューの起動記録を通らないため、`no open request` だけでは未起動と判断できません。
デバッグモードの小さなペインではツールバーをスクロールできます。
v0.1.2では、小さなペインで編集ツールバーが描画領域を圧迫してCanvasの高さが0になる不具合を修正しました。
v0.1.1の `render ready` はレンダラー生成完了のみを示し、実際の描画完了を示すものではありませんでした。
v0.1.3では初回描画とサイズ変更時の描画を同期実行し、初回表示を `requestAnimationFrame` の実行待ちにしません。
操作時のフレーム予約とキャンセルにはCanvasが属するウィンドウを使います。
`frame scheduled` は操作によるフレーム予約、`renderer disposed` は描画処理の破棄を示します。
この変更は初回フレーム待機への対策であり、この変更だけではObsidian実機で報告された症状は解消しませんでした。

v0.1.4の診断コマンドは、コピー可能なダイアログにビューごとの状態と直近64件のイベント履歴を表示します。
`V` はビューID、`L` は読込IDです。
`clearBoard` に破棄理由、描画処理の有無、呼び出し元を記録し、別ビューの終了と対象ビューの再読込を区別できます。
古い読込の中断は履歴だけに残し、新しい読込の状態を上書きしません。
ファイル切替後に古いファイルの解除通知が届いても、新しい描画処理を破棄しないようにしました。
これらの順序はAPIスタブで検証しており、実機で同じ順序が発生したと断定するものではありません。
`renderer disposed` 単独では、再読込、ファイル解除、ビュー終了、別ビューの終了のどれかを判別できません。

v0.1.5では、独自の読込メソッド `loadFile` がObsidianの `FileView` 内部メソッドと衝突する問題を修正しました。
ユーザーの履歴では、`setState` から独自メソッドが直接呼ばれ、公開フック `onLoadFile` を通らず描画した直後にビューが終了していました。
独自メソッドを `loadPurBoard` に変更し、基底クラスによるファイル設定と `onLoadFile` 呼び出しを妨げないようにしています。
基底クラス相当の `setState` → `loadFile` → `onLoadFile` 呼び出しを使う回帰テストでは、修正前にファイル参照が未設定となること、修正後にファイル参照と復元用の状態が保持されることを確認しました。
このテストはObsidian内部実装全体の再現ではありません。
2026年11月5日、ユーザーからv0.1.5で「開けるようになりました」と報告があり、デスクトップ版Obsidianで今回の起動と表示の不具合が解消したことを確認しました。
編集操作全般やAndroid版での確認を意味するものではありません。

## 操作

| 操作 | 動作 |
|---|---|
| 画像を左ドラッグまたは1本指でドラッグ | 選択した画像を移動（初期状態の編集モード） |
| 空白またはマウスの中央ボタンでドラッグ | ボードを移動 |
| 2本指のピンチと移動 | 指の中点を基準に拡大縮小しながら移動 |
| マウスホイール | カーソル位置を基準に拡大縮小 |
| ビューヘッダーの「PUR操作」アイコン、ビューのメニュー、右クリック、650msの長押し | 保存、Undo / Redo、回転、反転、全体表示など |
| ボードにフォーカスして `0` / `+` / `-` / 矢印キー | 全体表示 / 拡大 / 縮小 / 移動 |
| PURビューにフォーカスして `Ctrl+S`（macOSでは `Cmd+S`） | 現在の `.pur` を上書き保存 |
| 編集モードのPURビューにフォーカスして `Ctrl+V`（macOSでは `Cmd+V`） | クリップボードの対応画像をビュー中央へ追加 |
| 編集モードのPURビューへSVGデータURLを貼り付け | URLを復号したSVGをビュー中央へ追加 |
| OSの画像ファイルをボードへドロップ | 対応画像をドロップ位置へ追加 |
| PUR操作メニューの「保管庫から画像を追加」 | 保管庫内の対応画像を選んでビュー中央へ追加 |
| PUR操作メニューの「選択した画像を削除」、ボード上の `Delete` / `Backspace` | 選択した画像を削除 |

初回は画像全体が収まる表示になります。
PureRefに保存されたカメラ位置は復元しません。
Markdownの `[[board.pur]]` のようなファイルリンクは対象ですが、ノートへの `![[board.pur]]` 埋め込み表示は実装していません。
背景グリッドはボード座標に固定し、パンとズームに追従します。
v0.3.2では100ボード単位の2倍または半分刻みで間隔を変え、画面上の間隔を48px以上96px未満に保ちます。
ズーム時はボード座標の原点を共通にして段階的に細分または統合し、パン時は同じボード位置の線が移動します。
画面内だけを各軸256本以下で描画します。
グリッドは画像の背面に描き、`.pur` や画像へ焼き込みません。

コマンドパレットの「現在のPURを保存」「PURの編集を元に戻す」「PURの編集をやり直す」「PURを全体表示」「PUR操作メニュー」も使えます。
これらの操作コマンドはアクティブなPURビューだけを対象とします。
他のノート上の `Ctrl+S` は横取りしません。
Obsidian標準の「現在のファイルを保存」のキー設定はそのまま残してください。
プラグインの「現在のPURを保存」には同じキーを割り当てる必要がありません。
すでに重複割当した場合は、PUR専用コマンド側の `Ctrl+S` / `Cmd+S` だけを解除してください。
PURビュー専用の公開API `View.scope` と `Scope` で `Mod+S` を処理し、標準保存のアプリ側スコープへ重複して流しません。
他のビューではこのPURスコープは使われず、標準のノート保存を維持します。
入力欄でのキーは保存操作として扱いません。
公開 `FileView` にはバイナリー用の標準保存フックがなく、`TextFileView` の文字列保存へ置き換えると `.pur` を壊すため、標準保存コマンド自体の差し替えは行いません。
この文脈限定キーは固定の `Mod+S` であり、標準保存コマンドのキー設定を自動追従するものではありません。
Androidではビューヘッダーやビューのメニュー、ボードの長押しから保存でき、キーボードは不要です。
長押しの実端末での操作感は未確認です。

## 画像を編集する

ボードを開くと編集モードになります。
対応画像をタップまたはクリックすると選択枠を表示し、画像本体をドラッグすると画像を移動できます。
選択枠は水色の細い実線で、四隅と各辺の中央に計8個の小さい丸ハンドルを表示します。
どのハンドルでも、対向するハンドルの位置を固定し、縦横比を保って拡大縮小します。
辺の中央のハンドルも片軸だけの変形にはしません。
ドラッグ開始位置から対向点とハンドルを結ぶ方向への移動量で倍率を決めるため、丸の中心から少しずれた位置を押しても画像が跳びません。
対向点を越えても反転させず、1回の操作は開始時の0.05倍から20倍に制限します。
既存の回転、反転、せん断を含む変換も保持します。
丸の表示半径は画面上の3pxで、判定半径はマウス9px、タッチ22pxです。
判定領域が重なる場合は最も近いハンドルを選びます。
PUR操作メニューで「閲覧モードへ」を選ぶと、画像上のドラッグを含む単指操作がボードのパンに戻ります。
空白部分のドラッグは編集モードでもボードのパンです。
2本指のピンチと移動はどちらのモードでもボードのズームとパンになり、選択画像の位置は変わりません。
選択枠は表示されている画像項目の矩形に沿い、ピクセル単位の切り抜き境界には沿いません。

## 回転と反転

選択中の画像は、右クリック、モバイルの長押し、またはPUR操作メニューから90度時計回りまたは反時計回りに回転できます。
同じメニューから左右反転と上下反転も実行できます。
操作は選択画像の中心を維持し、1回ごとにUndo / Redo履歴へ記録します。

自由回転は、選択枠の四隅から画面上20px外側の操作域をドラッグします。
回転操作域にはハンドルを描画せず、マウスを乗せると回転カーソルを表示します。
拡縮用の丸ハンドルは8個とも残し、ホバー時には画像の向きに沿ったリサイズカーソルを表示します。
修飾キーは不要で、角度スナップは行いません。
回転は1本指で操作し、2本目の指を置くと現在までの回転を確定して通常の2本指カメラ操作へ切り替えます。
拡縮と回転の各ポインター移動では、予約フレームの実行を待たずCanvasを同期更新し、画像を変換後の位置へ描画します。
「設定」→「LazyRef PUR Viewer」→「デバッグモード」を有効にして操作すると、診断履歴に操作ごとの`pointerMoves`、`drawCalls`、`renderedFrames`が記録されます。
描画例外は同じ履歴に`draw failed`として記録し、続けてエラー通知します。
不具合を調べる際は、ビルド番号が`0.12.0`であることを確認し、1本の画像を選択して拡縮または回転し、操作を離した後に「PURビューアーの診断情報を表示」を実行してください。
`pointerMoves=0`なら操作中のポインター移動がレンダラーへ届いておらず、`pointerMoves`が正数で`renderedFrames=0`なら描画経路で失敗しています。
両方が正数なら操作中のCanvas描画処理は完了していますが、画面への提示が止まる症状はObsidian実機で別途確認が必要です。

回転と反転は画像の配置行列として保存され、Undo / Redo、未保存状態、自動保存、現在ファイルへの上書き保存に反映します。
コンテナー2.1の実fixtureを編集して保存し、再解析後に同じ変換行列が戻ることをテストしています。
PureRef本体で新機能の出力を開く実機確認はまだ行っていません。

## 画像の追加と削除

v0.12.0では、編集モードでPNG、JPEG、GIF、WebP、BMP、SVG、静止HEIC画像を元形式のまま追加できます。
クリップボードの画像はPURビュー内の貼り付けイベントで受け取り、入力欄や他のビューの貼り付けは横取りしません。
画像ファイルそのものとSVGデータURLを取り込みます。
通常のテキスト、HTTP URL、HTMLからの画像取得は行いません。
OSからのドロップは複数ファイルに対応し、保管庫内の画像は右クリック、長押し、ビューヘッダー、ビューのメニューから検索して選べます。
すべての追加方法で、実際に受け取った画像ファイルのバイト列と形式を変更せずに埋め込みます。
GIFとWebPのアニメーションは先頭フレームだけを表示しますが、後続フレームを含む元のファイルデータは保存します。
PNGへの変換、再圧縮、フレーム抽出は行いません。
既存PUR内の画像も表示のために展開するだけで、配置変更や保存で元の画像バイト列、形式、チェックサムを変更しません。
v0.9.1で追加時に行っていたPNG変換を取り除きましたが、すでにPNGとして保存された画像から元形式を復元することはできません。

クリップボードでは、OSとコピー元アプリがObsidianへ提供したファイルデータを保持します。
OSが元のGIFやWebPではなくPNGやBMPなどの変換済みデータを提供した場合、その受信データを保存します。
プラグインから元ファイルのバイト列を取得できるとは限らず、「クリップボードの受信データを保持する」ことは「コピー元ファイルと必ず完全一致する」ことを意味しません。
元ファイルの完全なデータを取り込みたい場合は、OSからのファイルドロップか保管庫内画像選択を使ってください。

画像の展開にはObsidianが使用するブラウザーの `createImageBitmap` を使います。
GIFとWebPはこのAPIが選ぶ先頭フレームを使い、画像の縦横とデコーダーが返す透過を保持します。
BMPは一般的なDIBヘッダー（12、40、52、56、108、124バイト）を対象とし、ビット深度や圧縮方式の対応は端末のデコーダーに依存します。
24bit BMPには透過がなく、32bit BMPでもアルファ情報が明示されていない形式の透過は保証しません。
WebP、BMPの一部の符号化や古いWebViewで展開できない場合は、対象形式とデコーダーの失敗理由を通知し、その画像は追加しません。
別のフレームや空画像へ黙って置き換える処理は行いません。

追加画像は元の画素寸法のまま、貼り付けと保管庫選択ではビュー中央、ドロップではドロップ位置を中心に配置します。
表示できないルート要素も含めた最大の `z` より前面へ置き、追加した画像を選択します。
複数ファイルは同じ位置へ順に追加し、各画像を1回のUndoとして記録します。
途中の画像が不正なら理由を通知し、その画像は追加せず、残りの画像の処理を続けます。

選択画像は操作メニューまたはボードにフォーカスした `Delete` / `Backspace` で削除できます。
追加と削除はUndo / Redo、変更の破棄、未保存判定、自動保存、上書き保存、別名保存に反映します。
削除を保存した後でも、現在のビューのUndoで画像を復元し、再保存できます。
既存画像の復元では、元の並び順、名前、フラグ、未知の項目列とTEXTの保存型も保持します。
保管庫の元画像ファイルは変更も削除もしません。

追加前に画像ヘッダーから寸法を確認し、1画像40MP、Undo用に保持する画像も含む合計80MPと画像データ64 MiB、10000画像の上限で拒否します。
展開後にも実寸を照合し、失敗した画像のメモリーを解放して通知します。
Undo用の展開済み画像はビューを再読込または終了するまで保持するため、削除だけでは追加可能なメモリー枠は増えません。
最終的な `.pur` も既存の64 MiB上限に収まる場合だけ保存できます。

保存では、既存の埋め込み画像用の `images.data` BLOBに元のファイルデータ、`format` にPNG、JPEG、GIF、WEBP、BMP、SVG、HEICの形式名、`checksum` にその元データのMD5を格納します。
このDB構造での保存とプラグインによる再読込は確認していますが、新規に埋め込んだ出力をPureRef本体が認識するかは、形式ごとの実機確認を要します。

## 選択時の前面化

v0.4.0では、編集モードで画像をクリックまたはタップして選択すると、その画像を最前面へ移動します。
標準はオンです。
右クリックのPUR操作メニューにある「選択時に最前面へ移動」のチェックで切り替えます。
モバイルの長押し、ビューヘッダーのPUR操作メニューにも同じ切り替えがあり、設定は再起動後も保持します。
オフでは画像の選択と移動だけを行い、重なり順を変えません。
設定の切り替え自体はボード編集ではなく、既に前面化した画像を元へ戻す操作でもありません。

前面化は重なり順の編集です。
未保存判定、Undo / Redo、上書き保存と別名保存に含まれます。
最前面の画像を再度選んでも、不要なUndo履歴を作りません。
クリック後にドラッグした場合は、前面化と移動を別の操作として記録し、Undoは移動、前面化の順に戻します。
閲覧モード、空白、右クリックによるメニュー表示、拡縮ハンドルを押す操作では前面化しません。
長押しでメニューを開いた場合と、単指移動前に2本目の指を置いてカメラ操作へ移った場合も前面化しません。
画像を既に単指でドラッグし始めてから2本指へ移った場合は、開始済みの移動と前面化が履歴に残ります。

形式2.1の描画順は `z`、同値なら有理数の `sort_order`、さらに同値ならID順として扱います。

`sort_order` と他要素の値は変更しません。
グループ内の子要素の `z` は別階層のため最大値へ含めず、グループ内画像の編集は従来どおり未対応です。
描画できないルート要素との関係も変わる編集なので、PureRefで開くと選択画像がそれらより前面になる想定です。

## 編集履歴と破棄確認

「元に戻す」「やり直す」と編集モード中の `Ctrl+Z` / `Ctrl+Y`（macOSでは `Cmd+Z` / `Cmd+Y`）で、画像移動や拡縮を操作単位で取り消せます。
「変更を破棄」は現在の編集を最後に上書き保存した配置（未保存なら読込時の配置）へ戻します。
未保存状態はデバッグモードの状態欄と診断コマンドで確認できます。
Undo後にすべての配置を保存済みの基準へ戻した場合は、未保存表示も解除されます。

**保存するまで、編集は現在のObsidianセッション内だけに保持します。**
通常の「保存」は現在の `.pur` に変更を書き込みます。
外部画像や未対応項目の編集はありません。
操作メニューの「ビューを閉じる」と、編集内容のある別ファイルへの切り替えには、破棄確認を表示します。
ファイルが外部で更新された場合も、未保存変更があれば破棄して再読込するか、編集中の表示を維持するかを選べます。
「編集を維持」を選んだ更新は、操作メニューの「外部更新を再読込」から後で読み込めます。

ただし、**Obsidianの公開プラグインAPIには、タブの閉じるボタン、ペインを閉じる操作、ワークスペースの一括閉鎖をキャンセルできるフックがありません**。
`FileView.onClose()` は終了を中止できない終了処理です。
そのため、これらの標準終了操作では破棄確認を保証できません。
未保存変更がある状態でタブを直接閉じた場合、画面を閉じた後に警告を表示しますが、編集内容は失われます。
アプリ自体の終了ではブラウザーの `beforeunload` 警告も登録していますが、ObsidianやモバイルOSが確認を表示するかは実機で未確認です。
閉じる前に確実な確認が必要な場合は、操作メニューの「ビューを閉じる」を使ってください。
このAPI制約により、**任意の閉じる経路を含めた破棄確認は未達成**です。

## 上書き保存と復旧用コピー

v0.3.0の「保存」は、現在開いているファイルを上書きします。

書き込む前に、同じフォルダーへ `元ファイル名.pur.lazyref-managed-ランダムID.bak` を新規作成し、読込時の元データと一致することを確認します。
同じ内容の管理コピーが失敗した前回処理から残っている場合は、バイト一致を確認して再利用します。
新規作成先が既に存在する場合は、上書きせず中止します。
バックアップの作成や照合に失敗した場合、元ファイルは書き換えません。
作成したコピーのパス、対応する元ファイルのパス、SHA-256をプラグインの `data.json` に記録してから元ファイルを変更します。
記録の保存に失敗した場合も元ファイルを変更せず、残っている候補のパスを通知します。
その後に元ファイルを再照合し、公開APIの `Vault.modifyBinary` で書き込み、保存先を読み戻して検証済み出力とのバイト一致を確認します。
使用中の公開API型定義にはバイナリー用の `Vault.processBinary` がありません。
`Vault.process` は文字列用なので、バイナリー保存には使用しません。
**読込と書込の間で外部アプリや同期処理が更新する競合を完全に排除する保証はありません。**
保存中はPureRefなど別アプリで同じファイルを編集せず、同期の競合にも注意してください。

保存成功時だけ、そのスナップショットを未保存判定と変更破棄の新しい基準にします。
Undo / Redoの履歴は消さず、保存前の状態へのUndoは未保存になります。
保存中に追加編集した場合は、その差分を未保存として残します。
自身の保存による `vault modify` は内容を照合し、編集中のビューを再生成しません。
外部更新が重なった場合は警告し、編集があれば破棄確認を行います。

失敗や部分書込、読戻し不一致があっても未保存の編集を保存済み扱いにしません。
復旧用コピーのパスを一時通知と診断情報に残し、デバッグモードでは状態欄にも表示します。
復旧用コピーを自動的に元ファイルへ戻すことはしません。
外部更新を上書きする事故を避けるため、編集と同期を止め、現在のファイルも退避したうえで、`.bak` のコピーを別名の `.pur` に変更して開いてください。
出力の検証成功後に限り、同じ元ファイルに対応する登録済みの古い管理コピーを削除します。
削除前には新しい復旧用コピーのSHA-256と古いコピーのSHA-256を照合し、削除対象のファイル実体と内容を再確認します。
他のファイルに変わっている場合や内容が変更されたコピーは削除しません。
正常終了後は1世代ですが、保存中は通常2世代分が一時的に必要です。
書込失敗、部分書込、競合で保存が未完了の場合は、従来のコピーも新しい復旧用コピーも削除せず保持します。
整理失敗時もコピーを残すため、失敗が続いた場合は1世代を超えることがあります。
ファイルの保存自体が検証済みで、古いコピーの削除や管理情報の更新だけに失敗した場合は、保存基準を更新したうえで「ファイル保存は完了、1世代整理は未完了」と一時通知します。
この場合は未保存の編集があるかどうかと、コピーの整理が完了したかどうかを区別してください。
次の保存成功時に登録済みの残存コピーを再照合して整理します。
新しいコピーを残したまま古いコピーを消す順序にし、元ファイルと唯一の有効な復旧データを先に壊さない構成です。

プラグインが有効な間にObsidianから元ファイルやフォルダーを改名した場合は、管理情報のパスを更新します。
元ファイルだけを改名しても復旧用コピーの名前は変更しないため、以前の元ファイル名が含まれる場合があります。
コピーを含むフォルダーが改名された場合は、その移動後のパスを追跡します。
改名先に別の管理情報がある場合はコピーを削除せず、その名前への上書き保存を停止して通知します。
必要なら「別名 .pur 保存」で未使用の名前へ保存し、元のコピーを手動で点検してください。
プラグイン無効時の改名や他端末での改名は自動追跡できず、旧名の登録とコピーが残る場合があります。
管理情報の保存失敗後は、同期と編集を止めて `data.json` とコピーを退避し、通知された問題を確認してください。
プラグイン更新時に `data.json` を削除しないでください。
管理情報が消えたコピーを名前だけで再登録して削除することはしません。
保管庫同期やObsidianのファイル履歴、OSのごみ箱が保持する別の世代は、この整理の対象外です。
バックアップの世代数を減らす変更であり、SQLiteや画像展開時の一時メモリーを削減する変更ではありません。

公開APIには、内容を条件にした原子的な削除もありません。
削除直前まで照合しますが、同時に他アプリや同期がコピーを置き換える競合を完全には排除できません。
保存中は元ファイルだけでなく復旧用コピーとプラグイン設定も、他端末や他アプリから変更しないでください。
通常保存で元ファイル不変だったv0.2.0とは異なります。

### アイドル時の自動保存

自動保存までの待ち時間は、「設定」→「LazyRef PUR Viewer」→「自動保存までの待ち時間」で変更できます。
値は1～60秒の整数で、初期値は従来どおり3秒です。
設定はプラグインデータへ保存され、Obsidianを再起動しても保持されます。
スライダーでは0秒や範囲外の値を指定できません。
設定データに欠落、非整数、範囲外の値があった場合は初期値の3秒を使います。
設定保存に失敗した場合は一時通知を表示し、スライダーを保存済みの値へ戻します。
短時間にエラーが続いても通知は1件を更新して表示し、後の設定保存が成功したら閉じます。
設定保存APIの完了後に保存値を読み戻して照合し、一致を確認してから実行中の間隔へ反映します。
保存値が読み戻せない場合は未検証の間隔を適用せず、失敗通知を表示します。
他のプラグイン設定項目も既存データから引き継いで保存します。
未保存編集がある状態で待ち時間を変えると、新しい秒数をその時点から数え直します。
保存中に設定を変えても進行中の保存には割り込まず、保存後に未保存編集が残っていれば新しい待ち時間で再予約します。

編集を止めて設定した時間が経過すると、現在の `.pur` へ自動保存します。
画像をドラッグ中は操作イベントごとに待ち時間を延長し、操作が止まってから保存します。
Undo、Redo、前面化、画像の移動と拡縮も、未保存状態が残る編集として自動保存の対象です。
変更を破棄して未変更へ戻した場合は待機中の保存を取り消します。

保存処理中の編集は、処理開始時のスナップショットと照合して別の変更として扱います。
先行保存が成功した場合は、新しい編集をdirtyのまま残して設定中の待ち時間後に保存します。
先行保存に失敗した場合、追加編集がなければ無限再試行しません。
別名保存を開いている間も自動保存のタイマーを止め、操作後に未保存の編集が残っていれば、現在の `.pur` への保存を改めて待機します。
保存失敗、外部更新、削除、改名、ビュー切替の照合失敗は既存の一時通知に表示し、失敗した変更は未保存のまま残ります。
競合を解決するまで編集を続ける場合も、保存結果とNoticeを確認してください。

Obsidianが編集中のビューを閉じる前に `onClose` を呼んだ場合は、dirtyならその時点でも最終保存を試します。
既に保存中なら処理の完了を待ち、追加編集が残っている場合はもう一度保存を試します。
Obsidianの全てのタブ終了、アプリ終了、プロセスクラッシュで非同期の `onClose` が完了まで待たれる保証はありません。
したがって終了時保存は補助策であり、**終了操作の直前ではなく、設定した時間のアイドル保存を主な保護手段として使ってください**。
終了時の保存が失敗した場合は一時通知を表示しますが、ビューやアプリが先に破棄される経路では通知が見えない可能性もあります。
任意の閉じる経路で終了を拒否できるObsidian公開APIはなく、保存完了も強制できません。

### 旧バックアップの手動整理

v0.4.0以前の `元ファイル名.pur.lazyref-ランダムID.bak` には、所有と元ファイルとの対応を確定できる管理情報がありません。
この版は保管庫を探索して旧コピーを集めたり、名前だけを根拠に削除したりしません。
旧コピーは自動的に1世代へ減らないため、必要に応じて次の手順で整理してください。

1. Obsidianの保存と他アプリの編集、保管庫の同期を止めます。
2. 該当する元 `.pur` が正常に開けることを確認します。
3. その元ファイルに対応すると自身で確認できる旧 `.bak` だけを対象にし、必要なら保管庫外へ退避します。
4. 復旧に使うコピーを別名の `.pur` として開いて内容を確認し、残す世代を決めてから不要なコピーを手動で削除します。

不完全出力や管理未登録の候補についても、通知された個別のパスを確認してください。
不明な `.bak` をまとめて削除しないでください。

## 別名保存と書き込み対象

操作メニューの「別名 .pur 保存」では、新しいファイル名を入力します。
保存先は元ファイルと同じ保管庫内フォルダーです。
元と同じ名前、既存ファイル、フォルダーを含む入力、無効なファイル名は拒否します。
この操作は既存ファイルを上書きせず、別の形式への変換もしません。
現在のビューで行った画像の追加と削除は、別名保存にも含めます。
旧形式1.10は読み取りも含めて未対応です。

書き込み対象はコンテナー2.1、SQLite `application_id=940753918`、`user_version=200101` に限定します。
元DBを複製して、対応画像の配置変更では `items.transform` と `items.z` を更新し、追加と削除では対応する画像行と項目行を変更します。
配置だけの変更では `z`、前面化だけの変更では `transform` を更新しません。
QTransformは既存Rust実装と同じQVariantとlatin-1由来のTEXTで保存します。
ノート、グループ、未対応画像、未知のテーブル、その他の列と元の型は保持し、表示できない要素を削除しません。
更新トリガーが別のデータを書き換える可能性を避けるため、トリガーを含むDBは保存しません。
DB全体のバイト一致ではなく、未編集のSQL値と保存型の保持を対象とします。
元のコンテナーヘッダーとサムネイルを保持し、DBサイズとチェックサムを再計算します。
サムネイル、保存カメラ、シーン範囲、パスなどのメタデータは再生成しないため、PureRefでのプレビューや初期表示範囲が元の配置のままになる可能性があります。

別名保存中も配置のスナップショットを使い、元ファイルの内容とビューの読込IDを保存前後に照合します。
外部更新、ファイル名の変更、ビュー切替、終了、配置の変更を検出した場合は成功扱いにしません。
出力をメモリー内で再解析して配置を検証し、新規作成後に保管庫から読み戻してバイト列を照合します。
保存エラーや照合失敗では、残っている可能性のある保存先を通知します。
失敗時にそのファイルを自動削除したり、既存ファイルへ書き直したりはしません。
残ったファイルは不完全出力の可能性があるため、通知を確認し、使用する前に内容を点検してください。
保管庫の共通APIには外部同期を含む排他的なファイル操作がないため、他アプリや同期処理による同時書込を完全に排除する保証はありません。
保存中に保管庫や同期先から同名ファイルを作成しないでください。

別名保存後も現在のビューは元ファイルのままで、Undo履歴、Redo履歴、元ファイルに対する未保存表示を維持します。
「保存済みコピー」は保存時の配置を保存した別ファイルの名前であり、現在の配置まで保存済みという意味ではありません。
保存後にさらに編集しても、そのコピーは更新しません。
保存したコピーを保管庫から開くと、その配置を基準とした新しい編集セッションになります。
元ファイルに外部更新がある場合、古いDBから保存せずエラーにします。

実fixtureと未対応要素を加えたDBで、保存と再解析、未変更のSQL値の保持、元バイト列の不変、競合、保存失敗、保存中の状態変更を検証しています。
v0.2.0の保存と、その保存結果をPureRefで開けたことはユーザーによる確認済みです。
**重なり順保存、保存キー、自動保存、v0.6.0のバックアップ整理を含む上書き保存のObsidian実機動作、Android版での保存は未確認です。**
既存fixtureのパーサーで開けることだけを、すべてのPureRefファイルの互換性確認完了とはしていません。

## 読み込み計測

デバッグモード時だけ、表示ボードの上部にファイルサイズ、表示対象の画像数、画像の総画素数、読み込み時間を表示します。
読み込み時間は、ファイル読み出しを始めてから `.pur` の解析と画像展開が終わるまでを計測します。
画面へ最初に描画する時間や、以後のパンとズームのフレーム時間は含みません。

展開画像メモリーの値は、表示画像ごとの幅と高さの合計に4 byteを掛けた概算です。
同じ元画像を複数項目で使う場合は、表示項目ごとに画素数へ加算します。
これは画像をRGBAとして展開した場合の容量を見積もる値で、**端末またはプロセスのメモリー実測値ではありません**。
SQLite、元ファイル、Canvas、デコード時の一時バッファー、ブラウザーの管理領域などは含みません。
実際のメモリー消費量は端末、WebView、画像形式により異なり、このプラグインから共通に取得できません。

## メモリー使用量の制限

ファイルは64 MiB以下、画像と画像項目はそれぞれ10000件以下に制限しています。
保存寸法は1画像あたり40メガピクセル以下、デコード後の合計は複製も含め80メガピクセル以下です。
実際の画像寸法がDBの保存寸法と異なる場合もエラーになります。
項目の並び順を表すBigRationalは、分子と分母をそれぞれ1024個の32 bit桁までに制限しています。
Canvasの描画バッファーは長辺4096ピクセル、デバイス倍率2倍以下に制限します。

これは端末ごとのメモリー確保を保証する制限ではありません。
SQLiteの復元、MD5検証、画像展開はメモリー内で行い、解析処理はUIスレッドで動作します。
別名保存でも元ファイル、複製DB、出力、照合用の読込データを一時的に保持するため、閲覧時よりメモリーを使います。
保存処理のメモリー使用量は画像メモリー概算に含みません。
大きなボードでは表示待ちや端末のメモリー不足が発生し得るため、最初は小さなファイルで確認してください。
画像デコーダーは展開後に実寸を確認するため、不正な画像による一時的なメモリー増加までは防げません。

## RustとWASMを直接使わなかった理由

既存の `purcore` は `rusqlite` のbundled SQLiteを使い、`PurFile::read_bytes` で実ファイルの一時DBを作成します。
ObsidianのAndroid環境には、任意のネイティブRustライブラリーや実行時Node.jsを呼び出す共通APIがありません。
Rustのコンテナー処理とblob codecは、ファイルAPIを切り離せばWASM化を検討できますが、SQLite経路の変更と別のビルド構成が必要になります。

今回は既存の `docs\FORMAT.md` とRustコードを基準に、必要な読み取り処理をTypeScriptへ移植しました。
SQLiteには `sql.js` のasm.js版を同梱し、Obsidianの `Vault.readBinary` で取得したデータをメモリー内で読みます。
追加の `.wasm` ファイルや実行時のダウンロードはありません。
ビルドではsql.jsのブラウザー経路を固定し、Node.js向け経路を無効化しています。
既存Rustクレートと既存Android作業には変更を加えていません。

SQLiteのQVariant列は、通常のBLOBではなく、latin-1由来の文字列をTEXTとして格納しています。
sql.jsの文字列取得では埋め込みNULで切れるため、SQLでBLOBへキャストしてUTF-8全体を取得し、latin-1の元バイト列へ戻します。
既存のblob fixtureと実 `.pur` の両方を、この読み出し経路の確認に使用しています。

## 開発時の確認

```powershell
npm --prefix obsidian-pur test
npm --prefix obsidian-pur run build
npm --prefix obsidian-pur run test:browser
```

`test` は実fixtureからの画像データ、変換、切り抜き、寸法、チェックサム、元バイト列の不変性、未対応項目の警告、描画呼び出し順、カメラ操作、計測値と表示文言を確認します。
実fixtureへ未知のテーブル、インデックス、ビュー、ノート、グループを加え、保存前後のスキーマと未編集セルの型と値も比較します。
別名保存のダイアログから保管庫APIへの接続はObsidianのスタブで確認し、保存先競合、部分書込失敗、出力不一致、保存中の外部更新と編集変更を合成したテストで確認します。
上書き保存でも、復旧用コピー、外部更新、削除と改名、保存中のビュー終了、追加編集、保存基準とUndo / Redo、自己modify時の同一ファイル読込をスタブで確認します。
自動保存は初期値3秒、1～60秒の範囲、変更時の待機リセット、Undo後のdirty解除、保存中の間隔変更と編集追送、失敗後の無限再試行防止、ビュー破棄時のtimer取消を確認します。
設定タブのスライダー範囲、設定保存失敗時の表示値復元、再起動後の復元、他設定の保持も確認します。
設定APIのthis束縛、読み戻し不一致、連続失敗時の通知集約も確認します。
FileView統合では、アイドル保存、保存中に閉じた場合の待機、終了時の追加編集保存をObsidian APIスタブで確認します。
連続保存後の1世代と直前内容、管理情報からの再起動復元、ファイルとフォルダーの改名、作成競合、部分作成、部分書込、外部変更、削除失敗、管理情報保存失敗、旧コピーの非破壊も確認します。
通常時のツールバーと警告欄の非表示、デバッグ設定の即時反映、初期編集モード、PURビュー限定の保存コマンドとスコープ、失敗時の一時通知も確認します。
グリッド間隔の上下限、ボード座標との整合、パン追従、極端倍率での描画上限、回転や反転を含む8個のハンドルの等比拡縮と対向点の固定も確認します。
前面化の設定保存、無効時と閲覧時の不変、重なった画像のヒットテストとピクセル描画順、Undo / Redo、保存中の追加前面化、未対応ルート要素を含むDBの保存後再解析も確認します。
同じブラウザー向け設定でバンドルした解析コードを、Node.jsのAPIと通信を使えないVMでも実行します。

`test:browser` はループバックアドレスの一時ポートで検証ページを起動します。
表示されたURLをブラウザーで開くと、実fixtureの画像デコード、Canvasのピクセル一致、ホイール、合成タッチイベント、選択と移動、8個の丸ハンドルでの拡縮、Undo / Redo / 変更破棄を確認できます。
編集ツールバーを含む幅280px、高さ180pxのペインでの画像描画、非表示ペインの再表示、非同期描画の例外通知も確認します。
ツールバーと計測を非表示にしたときの描画領域拡張、グリッドを背面に描いたときの画像ピクセル保持も確認します。
形式2.1の編集結果をメモリー内で保存し、再解析、画像デコード、Canvasのピクセル一致、元ファイルと編集履歴の保持も確認します。
合成PointerEventによる結果は、物理端末の指操作やObsidianの閉じる操作を確認した結果ではありません。
テスト用サーバーは開発時だけ使用し、プラグインの動作には不要です。
確認後は `Ctrl+C` で停止してください。
このページはObsidian自体を起動するものではありません。

Obsidian実機では、拡張子の登録、ファイル一覧からの起動、Android WebViewの画像対応、端末の実タッチ、保管庫同期、プラグインの有効化と無効化を別途確認する必要があります。
